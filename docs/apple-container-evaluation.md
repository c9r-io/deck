# Apple container 作为可选 Linux 隔离运行环境：评估与设计备忘

- **文档性质：** 研究备忘 / 设计探索。
- **当前状态：** DEFERRED — NOT APPROVED FOR PROTOTYPING。
- **讨论日期：** 2026-10-09。
- **最终状态：** 已归档，暂缓，等待未来明确的产品需求与用户授权。

用户认可该路线值得保留，但尚未判断它是否符合当前产品优先级，因此暂不启动原型。

本备忘**不是**：

- 批准实现或批准试验；
- 正式路线图承诺；
- 新的生产安全契约；
- 当前版本必须完成的测试或发布门禁；
- 原 Protected 暂停结论（`docs/ce-calibration.md` Status）的撤销。

两个判断相互独立，不得互相替代：

1. **技术上：** Apple container 值得作为 Linux 隔离后端继续评估；尚无本项目原型实证。
2. **产品上：** 引入它的必要性、时机及长期维护成本尚未得到证明。

## 1. 背景与定位

〔契约〕Protected（受约束执行）目前是暂缓状态：Seatbelt 候选停在强制的生产支持性门 SB-7B（BACKEND_UNSUPPORTED）——Protected 需要的按会话动态自定义策略属于保留 / 未文档化行为，SDK 的 sandbox API 与 `sandbox-exec` 已弃用；SB-1..SB-6 与 SB-7A 是 NOT_RUN_AFTER_EARLY_STOP，不是通过。原 protected-v1 契约要求保留原生 macOS CLI 能力，`ce-calibration.md` 已写明 VZ Linux VM 无法满足它。

这个结论的范围是“动态自定义策略的生产支持性”，不要泛化成“整个 Apple App Sandbox 已被废弃”。

本次候选方向是：

> 保留 Full Local，另外提供可选 Linux 隔离运行环境。

不是：

> 透明地给现有 macOS 终端加上 sandbox。

〔上游〕按此前讨论引用的资料，Apple container 基于 Linux VM，普通 container 具有独立 VM 边界。这**不等于**可以运行现有 macOS 工具、使用宿主 Homebrew 二进制，或替代 Deck 的原生 macOS 构建与真实应用验收。

〔建议〕若未来正式研究，应为 Linux 方向单独界定目标。不要复用 protected-v1 名称，也不要把旧契约中无法满足的要求悄悄改成“不适用”。

## 2. 产品宪法审视

依据 `CLAUDE.md` 的现行原则：

- Deck 管理注意力，Agent 拥有工作。
- 环境选择可以属于会话协调，但不能发展为 Agent 工具执行调度。
- 可能的收益：减少用户对宿主误操作的担忧和反复确认。
- 可能的代价：新增镜像、登录、文件流转、网络、资源、恢复和故障排查负担。
- 评价对象是**总注意力成本**，而不只是隔离强度或机器启动速度。

尚未证明：这些收益足以覆盖新增复杂度；也未证明现在值得投入。

## 3. 候选架构〔建议〕

首选研究方向：

```
macOS Deck → 现有宿主 tmux → 受约束的 container 会话入口
           → Linux shell → Agent / 普通 CLI 及其子进程
```

- 整个交互会话进入 Linux 环境。不让 Agent 留在宿主、再由 Deck 判断哪些命令应该进入容器。
- 优先评估用户明确安装的官方 container CLI；暂不决定嵌入 Containerization 框架，不接管完整运行时平台。
- “每张隔离卡片一个独立环境，独立 HOME 和可写状态”可作为首轮候选基线，不是已经冻结的产品决定。共享可写目录仍会让不同环境相互影响，不能宣称完全互相隔离。

关键安全要求：

- 环境退出或连接失败后，不得落回可接收待发输入的宿主 shell。
- 不能自动从隔离模式降级到本机执行。
- 输入绑定当前环境实例、会话与终端 generation；替换后旧输入不得继续投递。
- 不向 guest 暴露宿主 Deck、tmux、MCP 或 container 的通用控制接口。

〔上游〕〔假设〕此前讨论指出 container machine 的便利默认值包括共享 HOME、SSH agent 等，不适合作为本提案的安全默认入口。具体行为与版本需在重启评估时核验。

## 4. 用户环境映射〔建议〕

| 项目 | 候选默认策略 | 可选授权 | 风险 / 注意 |
|---|---|---|---|
| 项目文件 | 用户选定内容的独立可写副本，不自动回写原目录 | — | 导入需考虑秘密文件、符号链接、未提交内容、子模块及 worktree 外部引用 |
| 共享目录 | 不共享 | 明确授权，区分只读和读写 | 只读不防数据外传；读写可能影响后续宿主操作 |
| HOME | 独立 Linux HOME | — | 不整体挂载宿主 HOME |
| 临时目录 | 环境内部存储，允许正常创建、执行、清理实验产物 | — | 不共享宿主 `/tmp` |
| 工具链 | Linux 镜像内提供，参考项目版本声明 | — | 不复制 macOS 二进制，不继承宿主 PATH |
| Shell / Git | 只筛选可移植设置 | — | 不整体执行宿主启动脚本；不无条件导入 helper、hooks 或 include |
| Agent 配置 | 独立 Linux 配置 | — | 不整体挂载宿主 Agent 配置目录；不自动继承 MCP、插件和 hooks |
| 登录 | 优先验证 Agent 官方登录流程；同一环境可保留登录状态 | — | 不默默把身份复制到新环境 |
| 凭据 | 不提供 SSH、云或 Kubernetes 凭据 | 必要时单独授权最小范围 | 见下 |
| 缓存 | 环境专属或明确隔离的 Linux 缓存 | — | 不默认共享宿主可写依赖缓存 |
| 导出 | 用户显式触发，目标明确 | — | 导出内容仍是不可信数据；不附带宿主执行、自动应用修改或配置导入 |

关于凭据，明确：

- 凭据一旦进入环境，就应视为环境内代码可能使用它。
- 本地隔离不限制凭据所赋予的远端权限。
- 删除环境不等于撤销可能泄露的凭据。
- 不为了首版体验直接建设通用凭据代理平台。

## 5. 网络（关键未决项）

本节没有任何一项已经解决。

〔上游〕〔假设〕此前资料中的 host-only、internal、关闭 DNS、代理环境变量等，不能直接等同于“禁止访问宿主或局域网”或“强制出站白名单”。

〔建议〕候选模式可以讨论断网、联网、受限联网；但只有后端实际实现并验证，才能成为产品承诺。

需要分开回答的四件事：

- 本地文件隔离；
- 数据外传控制；
- 宿主及局域网服务访问；
- 使用有效凭据操作真实云资源。

“开发服务发布到宿主”与“guest 访问宿主服务”是两个不同方向的授权。不能默认开放所有 localhost 服务，也不能为便利而自行修改系统网络规则。

## 6. 用户体验〔建议，非已批准规格〕

- 功能默认关闭，用户主动进入设置后再配置；启动 Deck 不自动弹指南、下载或安装。
- 新建卡片 / 项目预设选择“本机 macOS”或“Linux 隔离环境”，而不是一个模糊的全局安全开关。
- Full Local 保持原有能力，不因新增功能受到限制。
- 创建前展示摘要：项目输入方式、原目录是否可写、工具环境、登录、网络、额外凭据与资源。
- 高级明细展示挂载源 / 目标、读写模式、镜像身份和环境变量名称；不显示秘密值。
- 仓库配置只能提出环境建议，不能自行授予宿主权限。
- 卡片及终端持续显示运行位置；共享可写目录需明确提示；不用一个盾牌图标概括所有保护。
- 准备镜像、启动、连接和失败状态如实展示；目标身份建立后才能投递输入。
- 恢复不重放历史命令；停止保留数据；删除单独处理数据与凭据状态。
- 清理只作用于 Deck 明确拥有的资源；不使用影响其他工作负载的全局清理或服务停止。
- 容器文件链接不能盲目映射到宿主原文件。
- 拖放需要区分“复制文件”和“新增共享授权”；粘贴路径不自动获得访问权。
- 环境停止、连接中断或终端安静，不等于 Agent 任务完成。

## 7. Deck 特有的接入风险

### Signal

- 现有宿主进程树、peer PID 和前台 generation 证明，不能直接证明 guest Agent 的归属。
- 环境身份不等于当前交互客户端身份。
- 不接受 guest 自报宿主 pane 信息作为充分证明。
- 环境重建后旧事件失效。
- 容器化不会自动解决 Codex shared-daemon 的客户端归因问题（〔契约〕`CodexSignalTrust::Unavailable` 及相关调度 / 就绪门保持不变）。
- 继续保持 Signal 不产生授权；证据不足时诚实降级，不放宽自动投递。
- 原型可以暴露“状态不可用”，但正式产品必须评价这是否反而增加用户巡查负担。

### EDR / 运行时

- 〔上游〕此前讨论指出 Apple container 引入由 launchd 管理的外部服务和 helpers。
- 这与 Deck 当前进程面及外部依赖约束存在需要裁决的关系（见第 8 节）。
- 不能因为供应方是 Apple 就自动豁免。本任务不修改宪法或测试。
- 未来需评估：显式 opt-in 的外部运行时边界、来源与身份验证、升级行为和受管设备限制。

### 资源与生命周期

- 多卡片 VM 的真实内存、磁盘、启动与恢复成本未知。
- 镜像、卷、工作数据与凭据各自的生命周期需明确。
- 不把运行时客户端退出当成 guest 工作全部结束。

## 8. 与现行仓库契约的差异（2026-10-09 只读核对）

以下是归档时发现的差异，均未裁决，也没有据此改动任何契约：

1. **不属于 Protected 的现有重启条件。** `ce-calibration.md` 列出的三条 re-entry 条件中，第三条要求新后端满足冻结的 protected-v1 Security + Utility 契约，且不把 Deck 变成环境 / 容器平台；同文已写明 Linux VM 无法满足原生 macOS CLI 契约。因此本方向不满足任何一条，只能作为**另一条独立方向**记录，不构成 Protected 的重启。
2. **EDR-quiet 进程面是封闭白名单。** `tests/edr_quiet.rs` 头部规定：Deck 不触碰 launchd；只运行 bundle 内签名的 tmux；允许的 spawn 是固定 `/usr/bin` 工具、bundled tmux 与 `deck-mcp-runner`；bundle 外**唯一**的可执行例外是 Deck Tunnel Helper。调用用户安装的 container CLI 会是新的 bundle 外可执行与新的 spawn；其 launchd 服务虽非 Deck 自己创建，是否落入该契约的精神需要明确裁决。
3. **pane 可执行与恢复路径。** 普通会话是“纯 shell + `send-keys`”，恢复路径不出现 shell argv / 脚本，MCP 会话的 pane 可执行是签名的 runner。“受约束的 container 会话入口”作为 pane 进程将是新的一类例外。
4. **自动退休的证据。** 仅有的两条自动退休之一依赖 tmux `pane-died` 对拥有 shell 正常退出的记录，且“缺席不是删除授权”。入口进程退出（连接中断、环境停止）与 guest shell 正常退出是否可区分，未知；不能默认沿用。
5. **范围扩张审视。** `CLAUDE.md` 把环境 / 容器平台、worktree 所有权、Git/PR 编排列为需要特别、明确理由的范围扩张。项目副本、导出、镜像与卷生命周期都贴近这条线。
6. **测试机约束。** `AGENTS.md` 要求 Mac mini 上的实验不添加 launchd 任务、不在 home 下持久化可执行文件。未来若在该机器上试验外部运行时，需要先就此取得明确授权。

没有发现本备忘与现行契约之间需要立即处理的冲突：它不改变任何现行行为。

## 9. 重新评估触发条件

以下是判断“何时值得重启”的条件，不是待执行任务：

- 出现具体、重复发生的用户场景，证明现有 Full Local 的权限范围带来了明显注意力成本或误操作风险。
- 目标工作确实适合 Linux，用户接受平台差异。
- 有理由相信薄的会话环境适配即可提供收益，不要求 Deck 拥有 Agent 工作、Git 流程或完整环境平台。
- 网络、Signal、EDR 和资源成本存在值得验证的收敛路径。
- 用户届时明确批准新一轮调查或原型。

上游版本更新只是一条新信息，不自动触发研究或实验。

重启时先重读现行产品宪法、Protected 裁定和真实代码，再核验当时最新的 Apple 与 Agent 能力。不要照搬本备忘的版本假设。
