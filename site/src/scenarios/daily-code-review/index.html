Start a daily code review with Deck clock automations

Give a small code review a regular place in your workday. Start with one local repository and a one-step template, keep the result available to read, and decide when the session can end.

Checked against Deck 0.8.11 Stable on 9 November 2026. The project name and schedule below are examples. Use a repository you are allowed to inspect and an Agent CLI you already have installed.

1. Start with one small, read-only review

Choose one project and a fixed local repository directory. The example is a weekday review of uncommitted changes and the latest three local commits. It produces a short list of findings for you to verify; it does not fix code, run tests or fetch new commits.

First open an ordinary Deck session in that directory. Check the directory and branch, start your installed claude or codex --no-daemon, and deal with sign-in, trust and permission choices yourself. Use the CLI's own permission controls for the access you intend. Deck does not install a CLI, provide its account or restrict its tools. The CLI may contact its model provider and incur its usual charges.

If you want reported input requests and turn endings, enable the matching integration in Settings → Agents & notifications. Codex hooks also need review and trust in /hooks; --no-daemon uses a separate embedded session instead of shared-server continuity. Missing reports do not prove readiness. Check the signal limits.

2. Save a one-step review template

In the selected project, open Templates… from the New session ▾ menu, choose New template, and name it “Daily code review”. Put the following example into one step; a step can contain several lines. Keep this first trial to one prompt, with no repair or exit step.

Review this local repository without changing it. First report the current directory, branch and working-tree status. Read the uncommitted diff and the latest three local commits, then inspect the related code. Do not fetch, install dependencies, run tests, edit files, commit or push.

Return at most three concrete risks. For each, cite the file and line or commit, explain the evidence, and say what still needs human verification. Separate observed facts from hypotheses. If there is no relevant change or you cannot inspect something, say so. Do not claim that tests passed or that the code is safe.

This prompt is not a sandbox or a permission guarantee. It describes the intended task; the Agent still acts through its own tools and permissions. Read the proposed actions and any permission requests before accepting them. Adjust the review scope to your repository before saving.

3. Create the weekday clock rule

  1. From New session ▾, choose New on a clock…. Give the rule a recognizable name, such as “Morning code review”.
  2. Set Directory to the same repository, Command to the CLI you checked, and Group to where you want the new cards. Select your “Daily code review” template.
  3. Repeat every 1 week, select Monday through Friday, and choose a local time such as 09:30. These are weekdays, not a holiday calendar. Check the next three local times displayed before saving.
  4. For If missed, keep the default still start within 15 min. Under After the program exits, choose keep it so you can return to the result.
  5. Leave Send the first step to a newly started agent without waiting for readiness off. Save, then check the rule's next time in Automations….

For a first trial while you are present, use a time a few minutes ahead on a selected weekday. After reviewing that trial, edit the same rule to your morning time. Creating the rule, changing its schedule or resuming it from pause does not catch up slots earlier that day.

Keep the Mac awake and Deck running at the chosen time. Deck is not a remote scheduler that runs while your Mac is unavailable. If it resumes within the allowed grace period, a missed slot can still start; outside that window it is recorded as skipped. See the scheduling reference.

4. Check the first card before sending

At the slot, find the new card and open its terminal and ⏱ list. A card being created means the session started; it does not mean the review prompt was delivered.

With the default first-input choice, a fresh Claude or Codex session waits for a real interaction observed through its status integration, or your Send now after checking the target. Finish startup dialogs, check the directory and foreground program, then send the reviewed step once. Without the matching integration, automatic first input keeps waiting. Quiet output and elapsed time do not establish readiness.

If delivery is uncertain, inspect the terminal before retrying; a retry may duplicate the prompt. If the Agent requests input or permission, read and answer its actual question. Use the list's waiting reason to decide the next action.

Optional later: accept automatic first input

Once you understand the startup behavior, you can explicitly enable Send the first step to a newly started agent without waiting for readiness for this rule. It supports Claude, or Codex with literal --no-daemon. Its short compatibility wait is not readiness proof: a trust, update, sign-in or other startup dialog may receive the text and Enter. The choice covers only the first step; input requests, target checks and configured inspection checkpoints still apply. It does not approve Agent tools, prove the review is safe or verify its outcome. Leave it off if you do not accept that startup-input risk.

5. Read, verify, then deliberately close

When the Agent reports a turn ending, read the terminal. Check each finding against the cited code and decide which claims need a separate test or investigation. “No findings” is a report to assess, not evidence that the repository is correct. Deck does not judge task success. A turn ending does not prove the Agent or its background work has stopped.

Keep any useful summary in your own review record before closing. Keeping a card lets you return to the current session; it is not a guarantee of a durable transcript or process recovery across a machine restart. If you enabled human inspection on its list, complete that checkpoint too; merely viewing the terminal does not complete it.

While the previous run's card remains on the Board, the same rule's next slot is skipped, not queued. This applies even after you have read the result or the Agent has stopped. Moving the card to another group or closing only its pane does not release the slot. Closing it later does not replay the skipped run.

Once you have read the result and confirmed that the session can end, close the run's card. Closing a card ends its session and running programs. Review any scratchpad or reminder confirmation. Then check the rule's next time. If you need to retain the live session, keep it and accept that this rule will skip while the card remains; pause the rule when you want to stop future starts.

If today's review is missing

What happenedWhat to check
No new cardCheck the rule's recent runs and next time: was it paused, missed beyond its grace period, or skipped because its previous card is still open? Check that its group, directory and template still exist. There is no queued backlog to release by closing an old card.
Card exists; prompt is waitingOpen the terminal and ⏱ list. Resolve the displayed input, inspection or target condition; confirm startup readiness yourself before using Send now. Do not create a second rule as a workaround.
A turn ended; result unverifiedRead the findings and verify the evidence. A sent prompt or turn-ending signal is not a passed review. Close the card only when you intend to end that session.

After the first run, the routine is small: check the next slot, review the new card, record what you verified, and close the session deliberately. For several reviews or other work in parallel, use the attention workflow to decide what to open next.
